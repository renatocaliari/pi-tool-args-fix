# Cache-Friendly Repair Layer — Strategy & Plan

## Context

The `pi-tool-repair-layer` extension intercepts tool calls and results to fix common LLM argument mistakes. It does **two categories** of work:

| Category | Examples | Cache Impact |
|----------|----------|-------------|
| **Pre-execution repair** | null stripping, array wrapping, boolean coercion, JSON parsing, path cleaning, relational defaults | **Zero** — args modified before tool runs; conversation history unchanged |
| **Post-execution guidance** | error guidance injection, directory fallback, circuit breaker, staleness detection, empty search loop | **High** — changes `tool_result` text in conversation history → breaks prefix cache |

DeepSeek V4 Flash does byte-exact prefix matching (64-token blocks). Cache hit = $0.0028/M tokens, miss = $0.14/M (50× difference). Any change in the conversation prefix at any position invalidates everything after it.

---

## Strategy: Three-Pronged

### 1. Keep Pre-Execution Repairs (already cache-safe)

All `repairs/dispatch.ts` logic (null strip, array wrap, bool coerce, JSON parse, path clean, extra prop strip) and `applyRelationalDefaults` modify args **before execution** — the LLM never sees the repaired version. **No changes needed.**

### 2. Make Post-Execution Guidance Deterministic

Currently, guidance strings contain variable data (turn numbers, consecutive counts, etc.), which makes them non-reproducible across sessions. Fix: every error type produces a **fixed, deterministic string** based only on categorical inputs.

**Before (breaks cache):**
```
⚠️ File content has changed since it was last read (turn 12).
```

**After (cache-safe):**
```
⚠️ File content has changed since it was last read. Use the read tool to get the current content.
```

### 3. Separate Guidance from Tool Results via Internal Channel

Instead of injecting guidance into the `tool_result.content` (which goes to the LLM and enters conversation history), use the concept of an **internal-only guidance channel** — a separate message that is consumed by the system for state management but excluded from the conversation history sent to the LLM on future turns.

The `pi` coding agent framework processes tool results synchronously: the `tool_result` handler returns the content that the model sees on the *next* turn. To preserve cache, guidance should either:
- Return minimal deterministic responses (same error = same text), or
- Use a framework-level hook to add "next-turn context" that isn't part of the replayable chat transcript

## Implementation Plan

### Phase 1: Determinize Guidance Strings

**Files:** `repairs/guidance.ts`, `recorder/classifier.ts`

Remove all dynamic/stateful values from guidance strings:

| Function | Currently Contains | Fix |
|----------|-------------------|-----|
| `buildStalenessGuidance(lastReadTurn)` | `(turn ${lastReadTurn})` | Remove turn reference; use static text |
| `buildCircuitBreakMessage(toolName, count, details)` | `"failed ${count} consecutive times"` + error details | Use fixed text without count/error details |
| `buildEditLoopGuidance(consecutiveCount)` | `"attempt #${count}"` | Use static "repeated attempts" without count |
| `buildSequentialEditGuidance(...)` | `"${ordinalSuffix(count)} consecutive"` | Remove ordinal, use "Edit targets a region that was already modified" |
| `buildEmptySearchGuidance(pattern, count, toolName)` | `"returned no results ${count} times"` | Remove count, use "no results" |
| `buildEnhancedEditMismatchGuidance(...)` | Line numbers via file context | Keep context (it's deterministic for same file state) but remove line number variance from message |
| `getToolHelp(toolName)` (classifier.ts) | Contains possible causes / debug steps | These are already static — no changes needed |
| `buildPathValidationGuidance(paths, toolName)` | Lists specific paths | Keep as-is — paths ARE the categorical input |

**Detail:** For each function, ensure the output is purely a function of categorical inputs (error type, tool name, maybe a single path/pattern), not of turn count, consecutive count, or other internal state.

### Phase 2: Cache-Aware Error Handling

**File:** `index.ts` (tool_result handler)

Currently, on every error the extension:
1. Returns `{ content: [guidance], isError: true }` — guidance becomes part of the tool_result
2. This changes the conversation history → future requests have a different prefix → cache miss

**New behavior:**
- Return the **original error text** unchanged (no guidance appended) for the `content` field
- Store the guidance for the *next* turn's context only (if framework supports it)
- If no separate channel exists, limit guidance to **1 unique string per error category per session** — all occurrences of the same error get the exact same guidance text

This is the most impactful change: stop appending `🔧 Tool guidance` to every error result.

### Phase 3: Make Stateful Features Cache-Idempotent

**Files:** `index.ts`, `recorder.ts`

Stateful features that change behavior based on turn count or failure count always produce different results for the same turn differently.

| Feature | Current Behavior | Fix |
|---------|-----------------|-----|
| Consecutive failure tracking (3+ → CONSECUTIVE_LOOP, 7+ → circuit break) | Different responses at counts 1, 3, 5, 7 | After count >= threshold, all subsequent turns return the circuit-breaker response (not variant per count) |
| Empty search loop (3+ consecutive) | Guidance text changes with count | Same guidance at threshold and beyond |
| Guided error pairs (1st vs subsequent) | First error gets guidance, subsequent don't | This is already cache-friendly (1st guidance is deterministic, subsequent identical) — keep as-is |
| ContentHashCache staleness | Return "stale" status | Always return identical stalenes guidance text |

### Phase 4: Add Cache Metrics

**File:** `stats.ts`, `handlers/commands.ts`

Add tracking of how often guidance injection occurs per session:
- Count of tool_results that had guidance appended
- Break down by error type
- Show in `/repair-stats-session` command
- Add `/repair-cache-cost` command estimating cache misses cost

### Phase 5: Documentation

**File:** `AGENTS.md` or new `docs/cache-strategy.md`

Document the cache impact of each feature:
- Which operations are cache-safe (pre-execution repairs)
- Which operations break cache (guidance injection) and by how much
- How deterministic guidance preserves cache across identical sessions
- How to measure cache hit rate with provider API fields

## Summary of Changes

| File | Lines Changed | What |
|------|--------------|------|
| `repairs/guidance.ts` | ~80 | Determinize all guidance builders — remove turn counts, failure counts, variable data |
| `recorder/classifier.ts` | ~60 | Determinize `getToolHelp`, `getErrorGuidance` |
| `index.ts` (tool_result handler) | ~40 | Stop appending guidance to tool_result content; return original error text |
| `stats.ts` | ~20 | Add guidance injection tracking |
| `handlers/commands.ts` | ~30 | Add cache cost metrics command |
| `repairs/cache.ts` | ~5 | No content changes needed (already deterministic) |

The core insight: **pre-execution repairs are already free**. The only thing breaking cache is guidance appended to tool results. By making guidance deterministic, the same error produces the same tool_result text across sessions, enabling DeepSeek's disk cache to serve the common prefix after the first occurrence.
